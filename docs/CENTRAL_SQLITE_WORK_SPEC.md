# 미르감 중앙 Flask API + SQLite 전환 작업 명세서

작성일: 2026-10-06

상태: 설계 기준 문서. 2026-10-07 로컬 중앙 API·SQLite·클라이언트 연결과 CSV 초기 이전을 구현했다. 실행 방법·검증 범위·남은 배포 작업은 [구현 안내](CENTRAL_SQLITE_IMPLEMENTATION.md)에 기록한다.

## 1. 목표와 확정 범위

여러 PC가 같은 농장 계정으로 로그인하여 같은 고객·주문을 사용한다. 데이터 저장 동시성이 낮은 운영을 전제로, 별도 DB 서비스 없이 중앙 Flask API 프로그램 내부에서 SQLite를 사용한다.

개발 단계에는 중앙 서버와 기존 데스크톱 클라이언트를 같은 PC에서 서로 다른 프로세스·포트로 실행한다. 이후 중앙 서버를 다른 PC 또는 외부 서버로 옮겨도 클라이언트의 서버 주소 설정만 변경하여 연결할 수 있도록 한다.

### 포함

- 중앙 서버 프로세스와 기존 데스크톱 클라이언트 분리.
- 기존 CSV 컬럼을 유지하는 DB 스키마, 고정 고객·주문 ID 추가.
- 고객·주문·상품·로그인 데이터의 일회성 이전 도구.
- 기존 화면·탭 순서·톤앤매너·주문 입력 기능 유지.
- CSV 및 XLSX 고객 파일의 미리보기, 열 지정, 검증, 최종 반영.
- 기존 주문 CSV 저장·날짜 필터 다운로드 유지. 기존 고객·주문 엑셀 이전 경로 보존.
- 인증·농장별 접근 통제·중복 요청 방지·백업·두 클라이언트 검증.
- 서버와 클라이언트 각각의 Windows EXE 빌드 및 실행 안내.

### 제외

- 실제 호스팅 가입·결제·배포, 도메인 구매.
- SMS·택배 API 연동.
- 오프라인 DB와 중앙 DB의 양방향 동기화.
- 화면 전체 재작성, React/FastAPI로의 전환.
- 주문 헤더/주문 상품 테이블 분리, 가격·결제·정산 기능 추가.
- 일반 사용자를 위한 임의 주문 파일 업로드 UI, XLSX 주문 다운로드 신규 기능. 기존 기능과 별도 범위다.

## 2. 현재 코드에서 확인한 사항

| 영역 | 현재 구현 | 변경 방향 |
|---|---|---|
| 데이터 저장 | `apps/app.py`에서 pandas/csv로 직접 읽기·추가·덮어쓰기 | 서버 서비스와 DB 저장소로 이동 |
| 고객 기준 | 주문 검색·고객 관리 모두 `customer_upload_<계정>.csv` 사용 | 해당 파일을 고객 이전의 우선 원본으로 사용 |
| 별도 고객 파일 | `customer_<계정>.csv`도 존재하지만 현재 주 화면의 기준은 아님 | 두 파일 차이를 보고하고 자동 합치지 않음 |
| 주문 | `order_<계정>.csv`, 현재 9개 컬럼 | 한 CSV 행을 한 DB 주문 행으로 이전 |
| 상품 | 모든 계정이 같은 `items.csv` 사용 | 1차 버전은 공유 상품 목록 유지 |
| 고객 등록 | 이름·전화번호·주소 모두 필수, 세 값 일치 시 기존 고객 반환 | 서버와 DB 제약으로 동일 규칙 유지 |
| 고객 삭제 | 이름·전화번호·주소 조합으로 대상 지정 | 고정 고객 ID로 대상 지정 |
| 주문 삭제 | 고객 조합과 날짜가 같으면 여러 행이 삭제될 수 있음 | 선택한 주문 ID 한 건만 삭제 |
| 파일 업로드 | CSV만 허용, 저장 후 `name,ph,address` 컬럼 검사 | 임시 보관 → 열 선택 → 검증 → 확인 → DB 반영 |
| 업로드 의미 | 기존 고객 보존 후 중복 제외 추가 | 완전 일치하는 고객은 건너뛰고 신규 고객만 추가 |
| 주문 저장 | 클라이언트 PC의 네이티브 저장 창으로 CSV 저장 후 이력 추가 | 저장 창은 클라이언트에 유지, 이력은 중앙 DB 저장 |
| 고객 정렬 | 이름, 주소 첫 단어인 시·도, 누적 주문 수량 내림차순 | 서버에서 같은 결과 계산 |
| 로그인 | `login.csv`의 이름·평문 비밀번호 | 계정 이전 시 비밀번호 해시로 저장 |
| 배포 | EXE 옆 `data` 폴더, 데이터가 Flask 정적 파일 경로에 있음 | 서버 데이터는 정적 경로·클라이언트 배포물에서 분리 |

관찰 근거: `apps/app.py`, `apps/templates/order.html`, `apps/templates/order_view.html`, `apps/templates/mypage.html`, `apps/migrate_order_new.py`, `apps/order_save_dialog.py`, `desktop_launcher.py`, `scripts/build_desktop.ps1`.

## 3. 실행 구조와 책임

```text
PC A: 브라우저 ── Mirgam 클라이언트(로컬 Flask, :5000) ──┐
                                                      ├─ HTTP/HTTPS API
PC B: 브라우저 ── Mirgam 클라이언트(로컬 Flask, :5000) ──┘
                                                            │
                                      MirgamServer(Flask API, :5100)
                                                            │
                                               SQLite: mirgam.sqlite3
```

개발 중에는 위 프로세스를 같은 PC에서 실행한다. 클라이언트 A/B 검증 시 로컬 화면 포트는 각각 5000/5001, 중앙 API 포트는 5100을 사용한다. 다른 PC의 127.0.0.1은 중앙 서버가 아니므로 실제 공유 환경에서는 서버의 LAN 주소 또는 HTTPS 주소를 설정한다.

### 중앙 서버

- SQLite 엔진은 서버 프로그램에 포함된다. 별도의 SQLite 서버 프로그램을 설치하거나 클라이언트가 DB 파일을 여는 구조가 아니다.
- Flask API + SQLAlchemy + Alembic, Windows 실행에는 Waitress 사용을 기본안으로 한다. Windows 지원 근거는 [Flask 배포 문서](https://flask.palletsprojects.com/en/stable/tutorial/deploy/)를 따른다.
- 데이터 조회·변경·검증·계정 권한·트랜잭션·가져오기 처리를 담당한다.
- 서버에서 사용자의 Windows 저장 창을 띄우지 않는다. 클라이언트 로컬 파일 경로를 받지 않는다.
- DB와 업로드 임시 파일은 정적 파일 경로 밖에 둔다.

### 데스크톱 클라이언트

- 기존 로컬 Flask와 HTML UI를 유지한다. 브라우저는 기존 로컬 URL만 사용한다.
- `api_client`가 중앙 서버를 호출한다. 브라우저가 중앙 API를 직접 호출하지 않으므로 1차 구현에 CORS 공개 설정은 필요 없다.
- 브라우저 쿠키에는 중앙 서버 인증 토큰이나 CSV/DB 파일 경로를 넣지 않는다. 무작위 로컬 세션 ID에 대응하는 토큰은 클라이언트 프로세스 내부에서 관리한다.
- 네이티브 저장 창, 클라이언트 다운로드 폴더, 입력 중 주문 초안, 파일 선택을 담당한다.
- 중앙 서버 장애 시 임의로 기존 CSV 저장으로 전환하지 않는다. 공유 데이터가 서로 갈라지는 것을 방지한다.
- 다른 PC의 변경은 새로고침·검색 재실행 시 확인한다. 실시간 WebSocket 동기화는 1차 범위가 아니다.

### 설정과 실행 방식

| 구분 | 설정 | 개발 기본값 |
|---|---|---|
| 중앙 서버 | `MIRGAM_SERVER_HOST`, `MIRGAM_SERVER_PORT` | `127.0.0.1`, `5100` |
| 중앙 서버 | `MIRGAM_SERVER_DATA_DIR` | `var/server/` |
| 클라이언트 | `MIRGAM_API_BASE_URL` | `http://127.0.0.1:5100` |
| 클라이언트 | UI 포트 | 5000 우선, 충돌 시 대체 포트 |
| 인증 | 서버/클라이언트 세션 비밀키 | 서로 다른 키, 설정 또는 최초 생성 파일, 소스에 고정하지 않음 |

아래 명령은 구현 후 제공할 CLI 계약이며, 현재 존재하는 명령이라는 뜻이 아니다.

```powershell
# 터미널 1: 중앙 서버. 기본은 루프백 바인딩.
python scripts/run_api_server.py --host 127.0.0.1 --port 5100 --data-dir var/server

# 터미널 2: 클라이언트 A
python scripts/run_client.py --api-url http://127.0.0.1:5100 --port 5000

# 터미널 3: 클라이언트 B
python scripts/run_client.py --api-url http://127.0.0.1:5100 --port 5001
```

개발용 편의 실행 스크립트는 별도 서버를 자동 실행할 수 있지만, 기본 클라이언트 EXE가 자기만의 중앙 서버·DB를 자동 생성해서는 안 된다. 운영 서버는 관리자가 한 번 실행하고 클라이언트는 같은 주소에 연결한다.

## 4. DB 스키마

원칙: 기존 컬럼과 값의 의미를 그대로 유지한다. 업무상 없던 주문 가격이나 다품목 주문 개념을 이번 이전에서 새로 만들지 않는다.

### 4.1 계정 `accounts`

- `id`: 고정 PK. 현재 농장 계정이 데이터 소유 단위다.
- `name`: 현재 로그인 이름, 유일값.
- `password_hash`: 기존 비밀번호를 문자열로 읽어 해시 생성. 원문은 DB·로그에 저장하지 않음.
- `customer_revision`: 고객 목록 변경 때 증가. 업로드 미리보기 후 다른 PC의 변경을 감지하는 용도.
- `created_at`, `is_active`.

여러 PC가 같은 계정으로 로그인하면 같은 데이터에 접근한다. 직원별 계정/농장 멤버십은 추후 확장 사항이다.

### 4.2 고객 `customers`

| 필드 | 설명 |
|---|---|
| `id` | 고정 PK, 화면 선택·삭제 기준 |
| `account_id` | 소유 농장 계정 FK |
| `name` | 기존 이름 컬럼, TEXT |
| `ph` | 기존 전화번호 컬럼, TEXT. 앞자리 0 보존 |
| `address` | 기존 주소 컬럼, TEXT |
| `is_active` | 현재 고객 목록 포함 여부 |
| `created_at`, `updated_at` | 관리 메타데이터 |

- DB 유일 제약: `(account_id, name, ph, address)`.
- 이름·전화번호가 같아도 주소가 다르면 다른 고객이다.
- 신규 등록과 파일 반영 시 바깥 공백만 제거한다. 하이픈 제거·주소 표준화·유사 고객 자동 병합은 하지 않는다.
- 신규 고객은 세 필드 모두 필수다. 기존 파일에 누락값이 있으면 이전 보고서에 표시하고 그대로 보존하되, 신규 주문 입력에서는 보완을 요구한다.
- 기존 고객을 삭제하면 비활성화하여 현재 목록에서 제외한다. 과거 주문은 유지한다.
- 완전히 같은 고객을 다시 등록하면 기존 ID를 재사용하고 활성화한다.

### 4.3 상품 `products`

- `id`, `item`(TEXT), `price`(TEXT, 기존 공란 허용), `is_active`, 관리 시각.
- 현재 전 계정 공용 `items.csv`의 의미를 유지한다. 농장별 상품 분리는 이번 범위에 자동 포함하지 않는다.
- `item`은 활성 상품 목록에서 중복 없이 표시한다. 같은 상품명의 가격 충돌은 이전 보고서에서 확인하고 자동 선택하지 않는다.
- 삭제는 비활성화, 과거 주문의 상품명은 유지.

### 4.4 주문 `orders`

| 필드 | 설명 |
|---|---|
| `id`, `account_id` | 고정 주문 PK, 소유 계정 |
| `customer_id` | 일치하는 고객 FK. 과거 주문이 현재 고객 목록에 없으면 NULL 허용 |
| `product_id` | 일치하는 상품 FK, 과거 미등록 상품은 NULL 허용 |
| `name`, `ph`, `address` | 주문 당시 수신 고객 정보 스냅샷 |
| `item`, `quantity`, `date` | 기존 상품·수량·주문일 값 |
| `sender_name`, `sender_ph`, `sender_address` | 기존 보내는 사람 정보 |
| `order_day` | 날짜 필터용 파생 YYYY-MM-DD, 해석 불가한 과거 값은 NULL |
| `batch_id` | 한 번의 저장 버튼으로 저장한 묶음 식별자 |
| `created_at`, `is_deleted` | 관리 메타데이터 |

- 기존 9개 컬럼의 이름·CSV 순서·문자열 값은 유지한다. `quantity`, `date`는 과거 파일 원문 보존을 위해 TEXT로 저장한다.
- 새 주문의 수량은 유한한 양수, 주문일은 유효한 YYYY-MM-DD로 검증한다. NaN/무한대/0/음수는 저장하지 않는다.
- 한 CSV 행 = 한 주문 행. 같은 날짜·고객·상품·수량의 동일 행도 별도 주문일 수 있으므로 주문 내용만으로 중복 제거하지 않는다.
- 신규 주문의 고객/상품 ID는 서버가 해당 계정 권한과 활성 상태를 검증한다. 클라이언트가 조작한 이름·주소를 신뢰하지 않고 서버 값으로 스냅샷을 만든다.
- 고객·상품 변경/삭제가 과거 주문 스냅샷을 수정하지 않는다.
- 고객의 누적 수량 정렬은 기존과 같이 현재 고객의 이름·전화번호·주소와 일치하는 삭제되지 않은 주문을 집계한다. 문자열 수량의 유효 숫자만 합산, 해석 불가 값은 0 취급하며 이전 보고서에 표시한다.
- 검색·날짜·계정·고객 FK 인덱스를 정의한다. 목록의 동률 정렬은 ID를 추가하여 안정화한다.

### 4.5 보조 테이블

- `auth_sessions`: 로그인 세션, 계정, 토큰의 해시, 만료/폐기 시각.
- `order_batches`: 계정별 `request_id` 유일 제약, 요청 본문 해시, 주문 ID 목록. 저장 재시도 시 중복 주문 방지.
- `customer_import_jobs`: 임시 원본 위치, 소유 계정, 파일 해시, 시트/헤더/열 매핑, 미리보기 결과, 고객 revision, 상태/만료 시각.
- `migration_runs`: 이전 실행 원본·파일 해시·계정·행수·결과. 같은 이전의 재실행 방지.

DB 파일, 관련 WAL/SHM 파일, 보조 테이블은 클라이언트나 정적 다운로드 URL로 공개하지 않는다.

## 5. 기존 업무 동작 유지 기준

### 고객 등록·선택·삭제

- 주문 화면의 이름 포함 검색, 작은 주소 표시, 선택 고객 토글을 유지한다.
- 브라우저 선택 키는 JSON 문자열 조합에서 서버가 반환한 `customer_id`로 전환한다.
- 같은 이름의 다른 주소 고객을 한 명 선택해도 다른 고객이 선택되지 않는다.
- 주문 화면의 ‘고객 추가’ 팝업은 중앙 서버에 등록하고 즉시 선택한다. 기존 주문 초안은 유지한다.
- 정확한 중복 고객은 기존 활성 고객을 반환하며 초안을 초기화하거나 고객을 해제하지 않는다.
- 고객 관리의 이름·지역·수량 정렬, 신규 등록·삭제를 유지한다. 기존 UI에 없는 독립 고객 편집 기능은 별도 범위다.

### 주문 입력·조회·삭제

- 고객별 상품·수량·주문일·보내는 사람 입력 및 전체 적용 토글 유지.
- 입력 목록의 인덱스, 약 8개 주문 높이의 고정 창과 스크롤, 하단 저장 버튼 유지.
- 달력 날짜 필터, 날짜 목록, 고객 검색, CSV 다운로드 유지.
- 주문 삭제는 선택한 `order_id` 한 건만 처리한다. 고객·날짜 기준의 여러 행 일괄 삭제는 계승하지 않는다.
- 한 저장 묶음에 잘못된 주문이 있으면 행별 오류를 보여주고 전체 저장을 중단한다. 조용히 잘못된 행을 누락한 채 성공으로 표시하지 않는다.

### CSV·엑셀 입출력

- 고객 입력: CSV/XLSX, 미리보기·매핑 후 반영.
- 고객 내보내기: 활성 고객의 `name,ph,address` UTF-8 BOM CSV를 제공하여 기존 작업 도구와 호환.
- 주문 입력 파일: 기존 `order_new.xlsx` 기반 이전 경로를 파괴하지 않는다. 중앙 DB 이전용 관리자 도구의 어댑터로 활용하며 원본을 변경하지 않는다.
- 주문 CSV 출력: 기존 9개 컬럼 순서와 UTF-8 BOM 유지. 내부 ID/계정/작업 메타데이터를 기본 CSV에 추가하지 않는다.
- 날짜·이름 검색을 다운로드에도 같은 조건으로 적용한다. 현재 이름 검색은 화면에서만 숨기는 방식이므로 중앙 API 조회 조건으로 통일한다.
- 기본 저장 폴더와 파일명 `YYYY_MM_DD.csv`, 사용자의 폴더·이름 변경 창 유지.
- 중앙 DB가 기준 데이터다. 배포 폴더의 과거 `order_<계정>.csv`에 계속 이중 쓰기하지 않는다. 동일 형식의 CSV는 다운로드로 생성한다.

## 6. 고객 CSV/XLSX 미리보기 및 열 선택

### 6.1 사용자 화면

1. **파일 선택**: ‘고객 엑셀·CSV 가져오기’, `.xlsx/.csv` 허용. 파일을 선택했다고 고객 목록을 바꾸지 않는다.
2. **시트·제목 줄 선택**: XLSX에 여러 시트가 있으면 선택. 기본 첫 비어 있지 않은 시트/첫 행을 제안하되 제목 줄 또는 제목 없음으로 변경할 수 있다. CSV 기본은 UTF-8/쉼표이며 CP949는 자동 감지해 선택할 수 있게 한다.
3. **열 지정**: ‘이름은 어느 열인가요?’, ‘전화번호는 어느 열인가요?’, ‘주소는 어느 열인가요?’ 세 선택창과 실제 예시 값 표시.
4. **미리보기 확인**: 지정한 세 열을 이름·전화번호·주소 형태로 보여주고 오류/중복/추가될 건수를 표시.
5. **최종 반영**: 기존 고객을 유지하고 신규 고객만 추가한다는 명확한 확인 문구. 최종 확인 전까지 DB의 고객 목록을 변경하지 않는다.

열 별칭을 이용해 후보를 미리 선택할 수 있으나 사용자가 확인해야 한다. 열 이름을 영어로 고칠 필요는 없다. ‘주문자’와 ‘보내는 사람’ 열이 함께 있으면 수신 고객 열을 직접 선택하도록 안내한다.

같은 제목의 열이 여러 개 있으면 제목만이 아니라 열 인덱스로 식별하고 `B열 연락처`, `F열 연락처`와 예시 값을 함께 보여준다. 세 역할에 같은 열을 중복 지정할 수 없다. 주소·상세주소를 두 열에서 합치는 기능은 1차 제외하며 한 열을 고르도록 한다.

### 6.2 검증 정책

- 완전히 빈 행은 무시한다. 데이터가 있는 행의 이름·전화번호·주소는 모두 필수.
- 누락/깨진 값이 있으면 엑셀 줄 번호, 문제 필드, 예시 값을 표시한다. ‘파일에서 수정 후 다시 선택’ 안내를 제공한다.
- 오류 행이 있는 상태의 부분 반영을 허용하지 않는다. 추가 시 기존 고객 목록은 보존한다.
- 유효 고객 0명인 파일은 전체 교체 불가. 파일 취소·만료·인코딩 실패도 DB 변화 없음.
- 전화번호는 처음부터 문자열로 읽는다. 숫자 셀 때문에 이미 앞자리 0이 사라진 경우 추측해서 보정하지 않고 확인 경고 및 재업로드를 요구한다. `.0` 숫자 표현이나 지수표기는 셀 타입/원문을 확인하여 표시하고 무조건 문자열 변환으로 저장하지 않는다.
- CSV 기본은 UTF-8 BOM/UTF-8과 쉼표다. CP949를 지원하며 해석 결과를 확인하고 인코딩·구분자는 사용자가 바꿀 수 있게 한다.
- XLSX 수식은 실행하지 않는다. 필요한 셀에 수식 또는 오류 셀이 있으면 사용자에게 값으로 붙여 넣어 다시 제출하도록 안내한다. 매크로 `.xlsm`·구형 `.xls`는 이번 범위에서 지원하지 않는다.
- 원본에서 같은 이름·전화번호·주소의 행은 하나로 합치고 제외 건수를 표시한다. 주소가 다르면 별도 고객.
- 추가 열은 고객 DB에 넣지 않고 원본에만 남는다. 열 매핑 외에는 기존 고객 반영 규칙을 바꾸지 않는다.

### 6.3 고객 추가 동작

2026-10-07 사용자가 고객 목록 교체 대신 중복을 제외한 추가 동작을 명시했다. 그 요청이 이전의 교체 기본안보다 우선한다.

- 미리보기: 새로 추가될 고객, 이미 등록되어 건너뛸 고객, 삭제 상태에서 복구할 고객, 파일 안 중복 건수를 표시.
- 최종 확인 문구: ‘새 고객만 추가하고 기존 고객은 유지하는 것을 확인했습니다.’
- 이름·전화번호·주소가 모두 같은 활성 고객은 건너뛴다. 파일 안에서 완전히 일치하는 행도 하나만 반영한다.
- 비활성 고객과 완전 일치하면 이전 ID로 재활성화한다. 파일에 없는 활성 고객은 그대로 둔다.
- 이 가져오기는 고객 삭제·대량 비활성화를 하지 않는다. 기존 주문도 유지한다.

### 6.4 서버 작업 수명 및 동시 변경

- 임시 작업은 계정별 `job_id`로 식별. 임시 파일은 무작위 서버 파일명으로 저장하고 원래 파일명을 경로로 사용하지 않는다.
- 업로드 초깃값: 최대 10 MiB, 데이터 행 20,000개, 미리보기 화면 50행, 작업 TTL 24시간. 압축 해제 용량·셀 개수에도 제한을 두고 운영 설정으로 조정 가능하게 한다.
- 첫 화면은 일부 행만 보여주지만 최종 반영 전에는 전체 행을 검증한다.
- 변경된 매핑의 결과를 별도 미리보기 버전으로 고정하고 최종 적용 시 그 버전을 요구한다.
- 미리보기 후 다른 PC에서 고객을 추가/삭제했으면 `customer_revision` 충돌로 409 반환. 추가 예정 내역을 다시 확인해야 한다.
- 중복 적용 요청은 기존 적용 결과를 반환한다. 작업 소유자가 아닌 다른 계정은 조회·적용 불가.
- 취소·만료 작업은 정리한다. 작업 적용과 고객 변경은 단일 DB 트랜잭션으로 수행한다.
- 사용자 파일을 기존 CSV 위치나 DB에 직접 덮어쓰지 않는다. 원본 파일과 DB 백업은 별도 취급한다.

## 7. 주문 저장과 로컬 파일의 실패 처리

중앙 DB 트랜잭션과 클라이언트 PC 파일 저장을 하나의 원자적 트랜잭션으로 묶을 수는 없다. 성공 상태를 구분해 중복 주문과 데이터 유실을 방지한다.

1. 클라이언트가 필수값을 확인하고 저장 위치·이름 창을 연다. 취소하면 서버 주문 변경 없음, 초안 유지.
2. 선택 경로의 상위 폴더 및 임시 파일 생성 가능 여부를 검사한다. 이 단계 실패 시 서버 저장을 시작하지 않는다.
3. 클라이언트가 묶음 `request_id`를 한 번 만들고 중앙 서버에 주문 저장 요청한다.
4. 서버가 전체 주문을 검증하고 하나의 트랜잭션으로 저장한다. 같은 계정·같은 request_id의 재요청은 같은 결과를 반환한다. 다른 본문이면 409.
5. 저장된 묶음의 서버 CSV를 내려받아 클라이언트 임시 파일에 쓰고 최종 경로로 교체한다. 대체 저장을 명확하게 안내하고 기존 파일 덮어쓰기 확인을 유지한다.
6. 중앙 저장과 CSV 저장 모두 완료하면 초안을 지우고 성공 건수·파일 경로를 표시한다.

예외 처리:

- 서버 응답 유실: 묶음 상태를 조회하거나 같은 request_id로 재시도. 확인 전 초안 삭제/새 request_id 생성 금지.
- 중앙 저장 완료 후 다운로드/파일 교체 실패: ‘주문은 저장됨 / CSV 저장 실패’로 표시. 초안을 저장 완료 상태로 보존하고 ‘CSV 다시 저장’ 제공. 새 주문 저장으로 반복하지 않는다.
- 서버 중단: ‘중앙 서버에 연결할 수 없습니다’ 안내와 재시도. 아직 저장되지 않은 입력 유지.
- 저장 창은 각 PC의 클라이언트에서만 실행한다. 서로 다른 PC의 저장 폴더를 혼동하지 않는다.

## 8. API 계약 초안

URL 접두사는 `/api/v1`. 중앙 서버가 현재 화면의 CSV 경로를 요청 인자로 받지 않도록 한다.

| 메서드·경로 | 기능 |
|---|---|
| `GET /health` | 기동·DB 연결·스키마 준비 상태, 개인정보 제외 |
| `POST /api/v1/auth/login` | 농장 이름·비밀번호 인증, 만료 있는 토큰 발급 |
| `GET /api/v1/auth/me` | 현재 계정 확인 |
| `POST /api/v1/auth/logout` | 중앙 인증 세션 폐기 |
| `GET /api/v1/customers` | 이름 포함 검색, 이름/지역/수량 정렬, 페이지 조회 |
| `POST /api/v1/customers` | 기존 등록 규칙, 중복 시 기존 고객과 created=false |
| `DELETE /api/v1/customers/{id}` | 해당 계정 고객 비활성화, 다른 고객/주문 유지 |
| `GET /api/v1/customers/export.csv` | 현재 활성 고객 목록 CSV |
| `POST /api/v1/customer-imports` | CSV/XLSX 임시 업로드, 작업·시트·열 정보 반환 |
| `POST /api/v1/customer-imports/{id}/preview` | 시트·제목 줄·세 열 매핑, 전체 검증·추가 예정 내역 반환 |
| `POST /api/v1/customer-imports/{id}/apply` | 미리보기 버전·명시적 교체 확인 후 트랜잭션 반영 |
| `DELETE /api/v1/customer-imports/{id}` | 작업 취소 |
| `GET /api/v1/products` | 기존 공유 상품 목록 |
| `POST /api/v1/products` | 상품 추가, 기존 가격 규칙 |
| `DELETE /api/v1/products/{id}` | 상품 비활성화 |
| `POST /api/v1/order-batches` | request_id + 주문 목록, 묶음 저장 |
| `GET /api/v1/order-batches/by-request/{request_id}` | 해당 계정의 저장 결과 조회 |
| `GET /api/v1/order-batches/{id}/export.csv` | 이 묶음만 CSV 출력 |
| `GET /api/v1/orders` | 날짜·고객 이름 포함 검색·페이지 조회 |
| `GET /api/v1/orders/dates` | 주문이 존재하는 날짜·건수 |
| `GET /api/v1/orders/export.csv` | 조회와 같은 필터, 페이지 제한 없이 결과 전체 출력 |
| `DELETE /api/v1/orders/{id}` | 선택 주문 한 건 삭제 |

- 일반 성공 응답: `data`, 목록은 `total/page/page_size` 메타데이터 포함.
- 오류: `error.code`, 사용자용 `error.message`, 필요 시 `error.details` 행/필드 오류.
- 401 인증 만료, 403 권한, 404 대상 없음, 409 변경 충돌, 413 파일 초과, 422 입력 오류, 503 일시적 저장 잠금/장애.
- 계정은 토큰으로 결정한다. 클라이언트가 다른 account_id를 보내 데이터 소유자를 바꿀 수 없다.
- health 응답에 API 계약 버전과 준비 여부를 포함한다. 클라이언트/서버 버전이 호환되지 않으면 데이터를 변경하지 않고 업데이트 안내를 표시한다. 파일 경로·계정 목록 등 내부 운영 정보는 공개하지 않는다.
- 목록은 페이지 처리하되 캘린더 날짜·총건수·내보내기는 전체 필터 기준이다. 현재 이름 검색이 페이지 내에서만 적용되지 않도록 서버 검색으로 통일한다.
- 검색의 `%`, `_` 등은 일반 문자로 취급한다. 정렬 컬럼은 허용 목록만 사용하고 SQL은 매개변수화한다.
- 읽기 요청은 제한된 재시도 가능. 쓰기 요청은 멱등성 계약이 있는 작업 외에 무조건 자동 재시도하지 않는다.
- 클라이언트 요청 타임아웃과 오류 안내를 통일한다. TLS 검증을 비활성화하지 않는다.

## 9. 데이터 이전·전환·롤백

### 이전 원본 선택

- 관리자가 이전할 디렉터리를 명시한다. `apps/static`와 `dist/Mirgam/data`는 서로 다른 상태일 수 있다.
- 실제 운영 데이터가 들어 있는 폴더를 우선 확인하고 하나를 선택한다. 소스 폴더와 배포 폴더, 백업 폴더를 자동 합치지 않는다.
- `order_new.xlsx`, `order_new.csv`, `order_<계정>.csv`를 동시에 읽어 주문을 이중 생성하지 않는다. 일반 이전은 현재 운영 `order_<계정>.csv`를 기준으로 하고 엑셀 이전은 별도 명시 모드다.
- `customer_upload_<계정>.csv`를 현재 고객 목록으로 사용한다. `customer_<계정>.csv`와 차이가 있으면 보고서에 남긴다. 파일 부재·형식 오류는 무단 대체하지 않고 관리자가 선택하도록 한다.
- 계정명과 파일명의 대응을 명시적으로 검증한다. 알려지지 않은 계정 파일은 보고하고 제외한다.

### 작업 절차

1. dry-run: 원본 읽기만 수행, 계정별 행수/중복/누락/컬럼/두 고객 파일 차이 보고.
2. 원본 전체 백업과 파일별 해시, 이전 보고서 보관. 비밀번호·전체 개인정보는 로그로 출력하지 않음.
3. 신규 서버 DB에 계정·상품·고객·주문을 트랜잭션으로 이전. 구형 6컬럼 주문의 보내는 사람 정보는 빈 문자열.
4. 정확히 일치하는 고객은 하나의 ID로 통합하되 고객 출처 행수와 통합 건수를 보고. 주문 행은 내용 중복 여부와 무관하게 모두 보존.
5. 현재 고객 목록에 없는 과거 주문 고객을 강제로 활성 고객으로 추가하지 않는다. customer_id는 NULL이고 주문 스냅샷은 보존한다.
6. 동일 이전 실행의 재시도는 migration_runs로 감지한다. 파일이 바뀌었으면 자동 전체 재이전하지 않고 중단·관리자 확인.
7. 출력한 9컬럼 주문 CSV와 원본을 문자열 기준으로 대조. 행수·총수량·날짜별 건수·고객 조합·보내는 사람·상품 비교. 문제 값도 삭제 없이 보고.
8. 실사용 전환 시 기존 CSV 쓰기를 중지하고 최종 이전·검증 후 모든 PC를 같은 서버에 연결한다. CSV/DB 병행 쓰기 기간은 두지 않는다.

### 롤백

- 중앙 DB 사용 전에는 기존 EXE와 보존한 CSV로 복귀 가능.
- 중앙 DB에 신규 주문이 쌓인 뒤에는 시작 시점 CSV만 복원하면 데이터가 유실된다. 쓰기를 중지하고 최신 DB를 기존 형식으로 내보낸 뒤 대조하고 복귀한다.
- 서버 업그레이드 전 DB 백업, Alembic 버전 확인 및 필요한 마이그레이션. 복원/재실행 테스트 없는 업그레이드를 배포하지 않는다.

## 10. 보안·운영·백업

- 인증 없는 고객/주문/파일 접근 금지. 모든 계정별 쿼리와 파일 작업에 소유 계정 필터 강제.
- 비밀번호는 Werkzeug 제공 해시 함수 등으로 저장하고 검증한다. 로그인 실패 속도 제한, 토큰 만료·로그아웃 폐기 구현.
- 브라우저 변경 요청에는 CSRF 보호, 로컬 클라이언트에도 Host/Origin 검증 및 무작위 세션 키 적용.
- 고객·주문·로그인 CSV를 EXE 기본 seed 또는 정적 폴더에 계속 포함하지 않는다. UI 정적 자원과 사용자 데이터 경로 분리.
- 파일 확장자만 믿지 않고 XLSX 구조·CSV 내용을 검증, 파일/행/셀/압축 해제 크기 제한.
- 로그에 비밀번호·토큰·주소록·전화번호를 기록하지 않는다. 오류 상세는 서버 로그와 사용자 안내를 분리한다.
- 중앙 서버는 기본 루프백 바인딩. LAN 공유는 명시 설정+방화벽 제한, 외부 접속은 HTTPS와 접근 정책을 갖춘 후 허용.
- 운영은 Flask 개발 서버/debug 모드가 아니라 WSGI 서버 사용. 서버 데이터는 로컬 영속 디스크에 보관.
- SQLite 연결마다 FK 활성화, WAL, busy_timeout을 설정하고 짧은 쓰기 트랜잭션 사용. 파싱·네트워크·저장 창 대기는 DB 트랜잭션 밖에서 수행.
- 서버는 SQLite 파일을 네트워크 공유 경로에서 열지 않는다. 다중 서버 수평 확장은 이번 구성에서 제외.
- 1일 1회 자동 백업, 고객 추가/이전/스키마 변경 전 추가 백업. 정상 백업 실패 시 가져오기를 진행하지 않는다.
- 실행 중 백업은 SQLite Backup API 사용. DB 본 파일만 복사하면 WAL의 미반영 데이터가 누락될 수 있으므로 원시 파일 복사로 대체하지 않는다.
- 백업은 서버 데이터 디렉터리 밖의 별도 위치에 보관, 초기 일일 보존 30개. 다른 디스크/외부 저장소 복사와 실제 복원 검증 포함.
- 서버 종료/장애 시 모든 클라이언트의 공유 저장이 중단됨을 운영 안내에 명시한다.

기술 근거: SQLite는 애플리케이션 서버 내부 DB로 사용할 수 있으며 한 DB에 동시에 하나의 writer만 허용한다. WAL 사용 프로세스는 같은 호스트에 있어야 한다. [SQLite 사용 지침](https://www.sqlite.org/whentouse.html), [WAL 지침](https://www.sqlite.org/wal.html). 실행 중 일관된 백업은 [SQLite Backup API](https://www.sqlite.org/backup.html)를 따른다.

최종 완료 조건: 위 필수 시나리오와 기존 회귀 테스트를 통과하고, 실행·초기 이전·백업·복원·업데이트 문서를 함께 제공한다. API/JS 자동 검증과 실제 Windows EXE 동작 검증을 구분하여 보고하고, 수행하지 않은 시각 검증을 완료로 표시하지 않는다.

## 14. 구현 시 유지해야 할 결정

1. 중앙 서버 내부 SQLite 하나가 기준 데이터. 클라이언트의 공유 CSV/로컬 DB 동기화 없음.
2. 기존 CSV 컬럼을 유지하는 평면 주문 스키마. 고정 ID·계정·이력 메타데이터만 추가.
3. 고객 업로드는 직접 반영이 아니라 열 선택 미리보기와 최종 추가 확인을 거침. 기본 제목 행은 1번째 줄, CSV 옵션은 UTF-8/쉼표.
4. 기존 목록을 보존하며 이름·전화번호·주소 완전 일치 고객은 건너뛰고 신규 고객만 추가.
5. 기존 전 계정 공유 상품 목록 유지. 상품 소유 범위 변경은 별도 결정.
6. 모든 파일 저장 창은 사용자 PC에서 실행. 서버 저장 성공과 로컬 CSV 저장 성공을 구분.
7. 과거 CSV는 이전 원본·백업·호환 출력으로 보존하며 DB의 실시간 이중 저장소로 사용하지 않음.
8. 계획 작성만 수행. 실제 데이터 이전·서버 배포·EXE 빌드는 이후 구현 작업에 포함.
